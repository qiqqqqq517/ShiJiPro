## 3. 缺陷清单与修复

### D1 采集阻塞主线程（性能）

**现象**（首轮冷启动取证）
```
I/Choreographer: Skipped 167 frames!
I/OpenGLRenderer: Davey! duration=1385ms
W/Looper: PerfMonitor doFrame : time=1187ms
```
**根因**：`AppViewModel.refresh()` 在 `viewModelScope`（默认 Dispatchers.Main）里直接调用
`cellular.read()`（`getAllCellInfo` 同步 binder）、`wifi.read()`（`scanResults`）、
`device.read()`（`StatFs` 文件 IO + `getMemoryInfo`）——全在首帧路径上。

**修复**：`app\src\main\java\com\shiji\pro\AppViewModel.kt`
- `refresh()` / `refreshCapabilities()` / `runSpeedTest()` 的采集段统一 `withContext(Dispatchers.Default)`；
- 引入 `RefreshSnapshot` 私有类承载后台计算结果，回主线程只做 `publish`（StateFlow.update 线程安全）；
- `onCleared()` 取消 GNSS 常驻订阅。

**验证**（修复后冷启动，n=3 复测）

★ **本报告初版的性能结论有误，此处更正。** 初版写「doFrame 1187→496ms（↓58%）」，
其中 496 实为 `am start -W TotalTime`，不是 `PerfMonitor doFrame time=` —— 两个口径被混为一谈，
且修复前只取了 n=1 的单次样本。现按 n=3 分别列出：

| 指标（口径） | 修复前 | 修复后 n=3 | 均值 | 降幅 |
|---|---|---|---|---|
| `am start -W TotalTime`（启动到首帧就绪） | 1181ms (n=1) | 545 / 513 / 496 | 518ms | **↓56%** |
| `PerfMonitor doFrame time=`（最重一帧主线程耗时） | 1187ms (n=1) | 861 / 760 / 763 | 795ms | **↓33%** |
| `Choreographer Skipped` 累计掉帧 | 167+40=207 (n=1) | 142 / 129 / 127 | 133 | **↓36%** |

三次均无 `AndroidRuntime` / `FATAL` / `ANR`。

更正后的结论：**采集离开主线程后启动指标确有改善，但最重帧仍有约 795ms，
初版「doFrame ↓58%」的说法不成立**。剩余 795ms 经 `PerfMonitor` 归因于
`ActivityThread$H w=110`（activityLaunch）与 `Choreographer$FrameDisplayEventReceiver`，
即 **Compose 首次组合本身**，已不在采集路径上；进一步压缩需引入 Baseline Profile，列为后续项。

另需说明取证局限：修复前仅有 n=1 样本，跨样本波动未测，故上表的「降幅」是
单次基线对三次均值的比较，只能视为方向性证据，不是精确回归量。后续若需硬结论，
应在同一构建上跑 ≥5 次并保留原始 logcat。

内存基线（前台稳态，供后续回归对照）：TOTAL PSS 119,492 KB / RSS 215,620 KB；
Java Heap 16,120 KB、Native Heap 27,716 KB、Graphics 23,636 KB；Views 13 / Activities 1 / AppContexts 5。

### D2 WiFi 未连接时哨兵值伪装「实测」+ 蜂窝信息串页（数据正确性，最严重）

**系统真值**：设备 WiFi **并未连接**，只开了个人热点（ap0），默认网络是 5G 蜂窝 ccmni1。
```
dumpsys wifi     → SSID: <unknown ssid>, BSSID: <none>, Supplicant state: DISCONNECTED,
                   RSSI: -127, Link speed: -1Mbps, Frequency: -1MHz, Net ID: -1, Security type: -1
dumpsys connectivity → Active default network: 100 = MOBILE[NR]，LinkAddresses 10.11.81.176/32
ip -4 addr       → 无 wlan0 地址；ap0 192.168.45.144/24
```
**修复前 App 显示（错误）**
```
信号(dBm)  实测 -127     频率(MHz)  实测 -1     链路速率(Mbps)  实测 -1
IPv4 实测 10.11.81.176   网关 实测 10.11.81.176（等于本机 IP）
子网掩码 换算 255.255.255.255   广播地址 换算 10.11.81.176
DNS 2408:8000:aaaa::, 58.240.57.33, 221.6.4.66
```
三条根因：
1. `WifiCollector` 第 78/79/81 行裸 `FieldValue.measured(info.rssi / freq / info.linkSpeed)`，无有效性判定；
2. 第 63-64 行用 `connectivityManager.activeNetwork` 取链路属性 —— activeNetwork 是**蜂窝**，
   于是蜂窝的 IP/网关/DNS 被当 WiFi 信息显示（掩码/广播是把蜂窝 /32 前缀套换算公式后的伪值）；
3. security 硬编码 N/A，注释称「需 API 31+」，实际 `WifiInfo.getCurrentSecurityType()` 存在（javap 已核验）。

**修复**
- 新建 `core\common\...\WifiValidity.kt`：纯 Kotlin 判定层（不 import android.\*，可 JVM 单测）。
  RSSI 合法闭区间 `[-120,0]`；频率/速率必须 `>0`；`SECURITY_TYPE_*` 15 个常量映射到领域枚举
  （数值经 `javap -constants` 逐个对拍：UNKNOWN=-1/OPEN=0/WEP=1/PSK=2/EAP=3/SAE=4/192BIT=5/OWE=6/
  WAPI_PSK=7/WAPI_CERT=8/EAP_WPA3_ENT=9/OSEN=10/PP_R1_R2=11/PP_R3=12/DPP=13；`LINK_SPEED_UNKNOWN=-1`）。
  连接态判据：`SupplicantState == COMPLETED` **且** `networkId != -1`。
- `WifiCollector.kt`：未连接时 `readConnection()` **直接返回 null**（不构造「全 N/A 的非空 connection」，
  否则界面会渲染一张标题为「已连接」的空卡片）；已连接时**弃用 activeNetwork**，改为遍历
  `getAllNetworks()` 用 `hasTransport(TRANSPORT_WIFI)` 选路，热点 ap0 与站点 wlan0 同为 TRANSPORT_WIFI 时
  优先 station 侧；三值与安全类型全部经 WifiValidity。
- `features\...\FeatureScreens.kt` WifiTab：`connection == null` 时渲染「WiFi 未连接」说明卡，
  展示采集器带出的判定依据，不渲染任何地址字段。

**验证**
```
WiFi 未连接
WiFi 未连接，不显示其它链路的地址信息（判定依据：SupplicantState=UNINITIALIZED 未握手完成，
且 NetworkId=-1（未关联））
因此本页不显示信号强度、频率、信道、链路速率，也不显示 IP / 网关 / DNS ——
周边热点（21） Alex -55 dBm ch5 / NTU -55 dBm ch1 / … （扫描不要求已连接，照常返回）
```
`-127 / -1 / -1` 与蜂窝 IP/网关/DNS 全部消失。

### D3 GnssCollector.observe() 无人订阅，定位与卫星恒空（数据正确性）

**现象**：位置页显示「卫星天空图（0 颗）」，无定位卡片。

**根因**：`GnssCollector` 的 `lastFix` / `satellites` 只在 `observe()` 的 `callbackFlow` 里
（LocationListener + GnssStatus.Callback 回调）填充；而全工程 `grep` 证实 `observe()` **无任何调用点**，
`AppViewModel.refresh()` 调的是 `snapshot()` —— 读的就是那两个从未被写过的字段。
即「数据源从未接通」，不是室内无信号。系统侧 `dumpsys location` 显示 network/fused 有定位
（31.976849,120.910801 hAcc=30.0），证明设备可用。

**修复**：`AppViewModel.startGnssStream()` 持有 `gnss.observe()` 常驻订阅，回调快照持续合并进单一数据源；
`refresh()` 不再覆盖 gnss（仅在尚无订阅数据时兜底一次）；`onCleared()` 取消订阅，由 `awaitClose`
触发 `removeUpdates` / `unregisterGnssStatusCallback`。

**验证**
```
logcat: LocationManagerService: registration onActive from uid: 10247 package: com.shiji.pro
位置页：卫星天空图（37 颗）
GPS SVID 23 方位 138.0° 高度 82.0° … / GLONASS SVID 15 方位 137.0° 高度 60.0° …
```
卫星数 0 → **37**。C/N0 全为 0.0、历书/星历/使用均 false 属室内无锁定的真实状态，
按「不伪造」口径如实显示，不做修饰。

### D4 设备页数值无格式化（可读性）

**现象**：`RAM 总量 实测 7848685568`、`尺寸(英寸) 换算 6.10598541197403`、`刷新率(Hz) 实测 144.00002`。

**修复**：新建 `core\common\...\Format.kt`（纯 JVM，`Locale.US` 固定小数点）
`bytesHuman` / `doubleShort` / `floatShort` + 三态安全扩展 `FieldValue<T>.displayTextWith`；
渲染侧新增 `renderFieldFmt`。**格式化只作用于显示层**：领域模型字段类型与原值一律不动
（CSV 导出与统计依赖原值）。`DeviceCollector` 同步收紧三态守卫：
`xdpi/ydpi/refreshRate` 走 `positiveFloat`（>0 且有限才 measured），
`ramAvailBytes` 判据由 `mi.totalMem > 0` 改为 `mi.availMem > 0`，ROM 两项走 `positiveLong`。

**验证**
```
尺寸(英寸) 换算 6.11     刷新率(Hz) 实测 144
RAM 总量 实测 7.31 GiB   RAM 可用 实测 2.56 GiB
ROM 总量 实测 463.99 GiB ROM 可用 实测 252.95 GiB
```

**数字校正留痕**：任务书原写 `498205687808 → 464.00 GiB`，实算
`498205687808 / 1024³ = 463.990204…`，HALF_UP 取 2 位为 **463.99 GiB**。
按项目纪律「断言写错改断言、不改实现」，以真值为准。
